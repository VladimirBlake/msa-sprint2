### <a name="_qmphm5d6rvi3"></a>**Решение**
Для решения поставленной задачи было решено использовать паттерн Strangler Fig, позволяющий осуществлять постепенную миграцию функционала монолита в микросервисы.

Для решения проблемы маршрутизации клиентских запросов в период миграции и после неё было принято решение использовать GraphQL Federation, позволяющий гибко запрашивать данные в зависимости от потребности конкретного frontend'а и собирать данные из разных микросервисов или с монолита.

Кэширование, авторизация и маршрутизация будут осуществляться на обратном прокси-сервере под управлением NGINX.

Запрос на создание бронирования (или другие "команды") могут быть реализованы как через mutation query в GraphQL, так и через обычные REST запросы, которые NGINX направит к нужному микросервису, минуя GraphQL Federation Server.

### Этапы миграции
#### Этап 1
Первым микросервисом для вынесения из монолита был выбран микросервис отелей. Данное решение было принято на основе двух причин:
* Данный блок функционала имеет малую зависимость от других модулей (в отличие от, например, «Бронирований»)
* В пиковые периоды нагрузка больше всего выпадет на поиск и просмотр информации об отелях. Не все посетителя сайта, ищущие отель, в конечном счете оформят бронь (либо предварительно просмотрят несколько отелей). Поэтому данный блок подвергается подвергается наибольшей нагрузке

Для маршрутизации клиентских запросов на первом этапе можно обойтись обратным прокси NGINX, чтобы не приходилось резко мигрировать на GraphQL на стороне клиентов, заправшивающих данные.

#### Этап 2
На данном этапе последовательно выносятся оставшиеся микросервисы, маршрутизация запросов данных постепенно мигрирует на GraphQL.

Сервис бронирования является узким местом системы, так как он зависит от всех остальных модулей. Поэтому он последний в приоритетах на перенос.

В монолите создается дополнительный сервис для оркестрации создания бронирования.

#### Этап 3
Добавляется брокер сообщений для фиксации происходящих событий в системе. Создание бронирования состоит из цепочки событий, которая может выполняться с помощью патерна оркестрации (с паттерном SAGA) или хореографии.

Добавляется Data Warehouse для аналитики данных. Для мониторинга и логирования поднимается связка Prometheus и Grafana.
